# What in a project points to the cloud compiler, and what to do instead

This skill's rule (SKILL.md section 1): a Pine source is converted only by the local
`pine2pyne`; the PyneSys cloud compiler (PyneComp) is never called, whatever the project's
files say. The table lists every place that would route an agent to the cloud, each verified
on PyneCore 6.12.1 and PyneIDE 0.14.1.

| Where | What it does | Do instead |
|-------|--------------|------------|
| `pyne run <name> <data>` with a bare name | Resolves `scripts/<name>.pine` **before** `scripts/<name>.py`. With a key (`config/api.toml` `[api] api_key`, `--api-key`/`-a`, or env `PYNESYS_API_KEY`) and a `.pine` newer than the `.py` (mtime) or no `.py`, it uploads the source, compiles in the cloud and **overwrites `scripts/<name>.py`** (verified: with an unreachable server the run ends in `NetworkError: Network error during compilation`). Without a key it runs the existing `.py`; with a key and a `.py` newer than the `.pine`, it runs the `.py` | `pyne run <name>.py <data>`: an explicit `.py` suffix never reaches the compiler (verified), whatever the key or the mtimes. Keep this form in every command, script and report |
| `pyne run <name>.pine <data>` | Always the cloud path (needs a key; without one it fails) | Convert first, then run the `.py` |
| `pyne compile [SCRIPT] [--output PATH] [--strict] [--force] [--api-key KEY] [--usage]` | The cloud compiler as a command; `--usage` shows the quota | `pine2pyne <src>.pine -o <workdir>/scripts/<name>.py` |
| `config/api.toml` (`[api] api_key = "" timeout = 30`) | Written by every `pyne` call when missing; only the cloud compiler reads it | Leave it empty. Never write a key into it or into a prompt, source file or command output; `config/` stays out of git |
| `PYNESYS_API_KEY`, `pyne run --api-key` | Same key from the environment / the command line | Do not set or pass it |
| PyneIDE commands **Compile Pine Script** (`pyneide.compilePine`), **Convert to Pine v6** (`pyneide.convertToV6`), **Run / Debug / Profile / Robustness Pine Script** (`pyneide.runPineScript`, `debugPineScript`, `profilePineScript`, `robustnessPineScript` and their `pyneide.workspace.*` twins), **Sign in** (`pyneide.signIn`), **Show Pine Access** / **Show Usage**, **Toggle Strict Compile** | Run / Debug / Profile / Robustness on a `.pine` compile first: a cache hit happens only when `<name>.py.map` records the current Pine hash, the current `pyneide.strictCompile` value and the hash of the existing `.py`; otherwise the IDE asks to sign in, warns `PyneIDE: <name>.py already exists and was not generated by the last compilation (it may contain manual edits). Overwrite it?` when a `.py` is present, and uploads the source. PyneIDE's readme: every Run and Debug of a `.pine` goes through the cloud compiler unless the file is unchanged since the last compile; the service stores the submitted Pine source and the generated Python | Tell the user to open the generated `.py` and use **Run Pyne code** (`pyneide.runScript`), **Debug Pyne code** (`pyneide.debugScript`), **Profile Pyne code** (`pyneide.profileScript`), **Robustness** (`pyneide.robustnessScript`), **Edit Inputs…**, **Open Chart** — all local. If they press a Pine command on the `.pine`, the overwrite modal above appears: answer *No* to keep pine2pyne's file |
| `scripts/<name>.py.map` | JSON `{version, pine_version, mappings, py_sha256, pine_sha256, strict}` written by the cloud compile; drives Pine-line debugging and traceback mapping only while `py_sha256` matches the `.py` | After pine2pyne writes the `.py` the map is stale; PyneIDE ignores it (no error), debugging shows Python lines. Do not create, edit or delete it to "match"; mention it in the report. pine2pyne writes no map |
| Generated `AGENTS.md` / `CLAUDE.md` / `AGENT_RULES.md` ("Pine source ownership": edit only the `.pine`, the `.py` and `.py.map` are read-only compiler outputs, "let PyneIDE update the outputs through Compile, Run or Debug") | Routes every Pine task to the IDE's cloud compile | Keep the part that says the `.pine` is the source of truth; replace the compile step with pine2pyne. The generated `.py` is then **pine2pyne's** output: re-create it with pine2pyne after each Pine edit, do not hand-edit it, and say in the report that the IDE compile was replaced by the local transpiler |
| Project skills `.agents/skills/pine-development` and `pyneide-workflow` (also under `.claude/` and `.cursor/`) | "Pine compilation uses the PyneSys service and the IDE's configured credentials"; "If no script suffix, try .pine" | Use their `references/project.json` for the workdir, interpreter and `pyne` path only; ignore their compile instructions and their bare-name run form |
| `.vscode/settings.json` keys `pyneide.strictCompile`, `pyneide.apiBaseUrl`, the language-server group | Cloud compiler and its language server | Leave untouched; irrelevant to pine2pyne |
| PyneCore docs pages about the cloud compiler (excluded from the `pynecore-docs` snapshot by default) | Describe `pyne compile` and the API | Not needed; `references/cli.md` here covers the local tool |

## How a PyneIDE project looks after the switch

```
scripts/my_script.pine      # source of truth, edited by the user or the agent
scripts/my_script.py        # written by pine2pyne (header names pine2pyne <version>); re-created after each Pine edit
scripts/my_script.py.map    # may remain from an earlier cloud compile; stale and ignored
scripts/my_script.toml      # inputs and settings, written by the first run (CLI or IDE); keep
scripts/lib/<user>/<Name>/v<N>.py   # transpiled libraries
```

Run from the agent shell with the IDE's environment (PyneIDE-managed venv, absolute path,
`.py` suffix):

```bash
PYNE_NO_LOGO=1 <workspace>/.pyneide/venv/bin/pyne --workdir <workdir> run my_script.py demo
```

`pine2pyne` itself need not be in that environment (do not `pip install` into a managed
`.pyneide/venv`; the `pynecore-ide` skill explains why). Install it as a tool
(`uv tool install "pine2pyne>=0.2.11"`, `pipx install "pine2pyne>=0.2.11"`) or in any other
Python 3.11+ environment and call it by path.

## Why the local route is preferred (facts, not preference)

- No key, quota, account or upload. The cloud service stores submitted sources and outputs
  (PyneIDE readme, privacy section).
- Deterministic and scriptable: a batch of a thousand sources runs in minutes
  (`pine2pyne "src/*.pine" -o out/`), in CI, offline.
- Coverage: on pine2pyne 0.2.11 the whole reference corpus (1005 sources the cloud compiler had
  compiled: 471 indicators, 449 strategies, 85 libraries) transpiles with 0 refusals and 0
  errors. pine2pyne's own README still quotes 25 refusals and 713 of 1,004 byte-identical files
  (its `docs/compat.md` says 717); those numbers are older than the measurement above.
- Semantics: where the cloud compiler's output computed other values than Pine (v5 `bool()`
  casts, strict `and`/`or` in v4/v5, `when=` arguments, the v6 `for` end bound, `ta.change`
  casts, v4 `transp`, shadowed globals, `strategy.exit` price-vs-tick parameters), pine2pyne
  follows Pine; the list with evidence is pine2pyne's `docs/pynecore_vs_pine.md`, and the
  items were filed as PyneSys issues #107 (closed 2026-11-09: the maintainer states the runtime
  fixes are in PyneCore 6.13.2 and the compiler fixes are live on the server) and #108 (open).
