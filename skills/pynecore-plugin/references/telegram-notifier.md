# Telegram notifications (`templates/pynecore-telegram`)

Plugin name `telegram`, class `TelegramPlugin(CLIPlugin[TelegramConfig])`.

## The options, and why a plugin

| Option | How | Fits when |
|--------|-----|-----------|
| A function in the script | `urllib.request` POST to the Bot API, called from `main()` under `barstate.isrealtime and barstate.isconfirmed` | one script, custom message content; the logic ships with the strategy |
| A shared library | the same function in `scripts/lib/<pub>/notify/v1.py`, imported by every script | several scripts, same chat |
| **This plugin** | a `logging.Handler` on `pyne_core_logger` + a wrapper around `alert()`; `pyne telegram` commands | every run of every script without touching them; also the runner's `[BROKER]` and quarantine lines that no script can see |

PyneCore has no notification hook. The plugin hooks what exists:

- `log.info/warning/error` in scripts and the live runner's `[BROKER] ...` / `sync engine
  quarantined ...` lines all go through the `pyne_core_logger` logger.
- `alert("text")` prints to the console; transformed scripts call it as `lib.alert.alert(...)`,
  which resolves the function through the module at call time, so replacing
  `pynecore.lib.alert.alert` intercepts every call.

## Install and configure

```bash
pip install -e <skill>/templates/pynecore-telegram
pyne telegram status                     # config path and effective settings (token masked)
pyne telegram test                       # one message, ignores `enabled`
pyne telegram send "deploy done"
```

`config/plugins/telegram.toml` (generated by the first `pyne` call after installing):

| Key | Default | Meaning |
|-----|---------|---------|
| `enabled` | `false` | Send during runs. `PYNE_TELEGRAM=1` in the environment also enables |
| `bot_token` | `""` | From @BotFather; `PYNE_TELEGRAM_TOKEN` overrides |
| `chat_id` | `""` | User, group or channel id (the bot must be a member; negative ids for groups); `PYNE_TELEGRAM_CHAT_ID` overrides |
| `min_level` | `"WARNING"` | Lowest script log level forwarded: `INFO`, `WARNING`, `ERROR` |
| `forward_alerts` | `true` | Forward `alert()` calls |
| `forward_broker` | `true` | Forward `[BROKER]` and quarantine lines, any level |
| `history_bars` | `false` | Also forward during the historical phase (backtests, warm-up); default realtime only |
| `prefix` | `""` | Prepended to every message, e.g. `[bot-1]` to tell instances apart |
| `api_base` | `https://api.telegram.org` | Bot API base; a relay or a test stub can replace it |
| `timeout` | `10.0` | Seconds per HTTP request |
| `rate_limit` | `20` | Messages per minute; the excess is dropped and counted in one appended note |

Message format: `[prefix] LEVEL text  (TICKER, bar time UTC)` for script lines, `[prefix] ALERT
text  (...)` for alerts, `[prefix] INFO [BROKER] ...` for runner lines. Token and chat id live
in `config/`, which PyneCore projects keep out of git.

## Behaviour during a run

- **Realtime gate**: script lines and alerts are forwarded only while `barstate.isrealtime` is
  true (the live phase), unless `history_bars = true`. A backtest with the plugin installed sends
  nothing (verified: `pyne run notify_probe file:BTCUSDT@60 -f -200` → 0 messages).
- **Broker lines** are forwarded regardless of phase (connection, reconnect, fills, quarantine
  with its `pyne broker resume RUN_ID QUARANTINE_ID` command).
- **Non-blocking**: the handler enqueues; a daemon thread posts with three retries and
  exponential backoff; permanent errors (`401` bad token, `400`/`403` bad chat) are reported
  once on stderr. The trading loop never waits on Telegram.
- **Rate limit**: a token bucket per minute. In the verified replay a warning on every bar hit the
  default 20/min cap within seconds and the alerts fell into the dropped count; set
  `min_level = "WARNING"` with sparse warnings, or raise `rate_limit`, and keep per-bar chatter
  at `log.info`.
- **Config refresh**: the handler re-reads the TOML at most once a minute, so `enabled` can be
  flipped on a running bot.

Activation path: the `pyne` CLI imports every installed plugin at startup; importing
`pynecore_telegram` runs `install()`, which attaches the handler and wraps `alert`. The handler
is dormant until the first record, when it resolves the workdir (`app_state` of the running CLI,
else `PYNE_WORK_DIR`, else the `.pyne` marker upwards from the current directory) and reads the
TOML.

Programmatic runners (`ScriptRunner` in your code, `../../pynecore-strategy/scripts/run_paper.py`): nothing imports the plugin
for you. `run_paper.py ... --import pynecore_telegram` imports it and exports the run's workdir
as `PYNE_WORK_DIR` so the plugin reads the same `config/plugins/telegram.toml`; in your own code
`import pynecore_telegram` (or `pynecore_telegram.install()`) after setting `PYNE_WORK_DIR`, and
do not strip the logger's handlers. `notify("text")` sends one message directly from any Python
code with the same configuration.

Not available: a `pyne run --telegram` switch. `cli_params("run")` options are parsed by the
CLI but not handed to plugins in 6.12, so the plugin reads its TOML and the environment instead.

## Verified (PyneCore 6.12.1, Bot API replaced by a local HTTP stub recording every POST)

| Check | Result |
|-------|--------|
| `pyne telegram status / test / send` | settings printed with the token masked; two POSTs to `/bot<token>/sendMessage` with `chat_id` and text |
| backtest `pyne run notify_probe file:BTCUSDT@60 -f -200` | 0 messages (history gate) |
| `pyne run notify_probe file:BTCUSDT@60 --live -f -200`, 12 s of replay, `min_level WARNING`, `rate_limit 500` | 87 messages: 78 `WARNING live bar ...`, 7 `ALERT tenth live bar ...`, 2 `[BROKER]` connect lines; each with `(BTCUSDT, <bar time> UTC)` |
| same with the default `rate_limit 20` | exactly 20 messages in the minute, the rest dropped |
| `run_paper.py notify_probe file:BTCUSDT@60 --bars 30 --import pynecore_telegram` | 33 messages: 30 warnings, 3 alerts, forwarded like the CLI run (`run_paper.py` hands its workdir to plugins through `PYNE_WORK_DIR` and keeps foreign log handlers) |

## Adapting the template

- **Discord / Slack / a webhook**: keep everything and change `_Sender._post` (URL and JSON body:
  Discord `{"content": text}` to a webhook URL, Slack `{"text": text}`); rename with
  `new_plugin.py telegram DEST --name discord --class DiscordPlugin`.
- **Email / SMS**: same place, a different transport; keep the thread and the rate limit.
- **Richer trade messages**: the plugin does not see fills directly. Log them from the strategy
  (`log.warning(f"filled {strategy.position_size} @ {close}")` on realtime bars) and they arrive
  through the handler; or read `output/<script>_trade.csv` in a separate watcher.
- **Per-instance routing**: run several bots with different `prefix` values, or different
  `chat_id` per workdir (each workdir has its own `config/plugins/telegram.toml`).
